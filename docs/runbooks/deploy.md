# Deploying iPro

Decision #100. iPro runs on AWS in Mumbai (ap-south-1), with backup copies and a key replica in
Hyderabad (ap-south-2). Deploys run from GitHub Actions (**Actions → Deploy → Run workflow**), from
`main` only. Staging first; production only after a reviewer approves.

## How it fits together

```
people ──HTTPS──► load balancer (+ web firewall) ──/api/*──► API tasks (Fargate) ──► RDS PostgreSQL 16
                        │                                        │                    S3 documents
                        └──────── everything else ─────► web tasks (nginx)           KMS field key
```

- **One address for both.** The app and the API share one origin (the cross-site check relies on it).
- **Migrations.** Each new API task runs the migrations in a first container, then starts. A lock
  lets only one task migrate at a time.
- **Bad deploys roll back.** If new tasks fail their health checks, the deploy rolls back by itself.

| Stack | Region | Holds |
| --- | --- | --- |
| `ipro-<stage>-prereq` | Mumbai | Image repositories (`ipro-<stage>-api`, `-web`), the app secret `ipro/<stage>/app` |
| `ipro-<stage>-dr` | Hyderabad | Backup copy vault and its key |
| `ipro-<stage>` | Mumbai | Network, database, documents, keys, backups, and the running app |
| `ipro-<stage>-dr-keys` | Hyderabad | Replica of the field-encryption key |

## One-time setup (per AWS account)

You need an AWS administrator for these steps; the pipeline never has these rights.

1. **Enable the regions.** Enable ap-south-2 (Hyderabad) in the account; Mumbai is on by default.
2. **Bootstrap CDK** in both regions:
   ```powershell
   cd infra
   pnpm exec cdk bootstrap aws://<account>/ap-south-1 aws://<account>/ap-south-2
   ```
3. **Let GitHub deploy without stored keys:**
   - Add GitHub's OIDC identity provider to IAM (`token.actions.githubusercontent.com`).
   - Create a role `ipro-github-deploy` that trusts it for this repository's `main` branch and the
     `staging` and `prod` environments.
   - Allow the role to assume the CDK bootstrap roles (`cdk-*`), push to ECR
     (`ecr:GetAuthorizationToken`, push and describe on `ipro-*` repositories) and
     `cloudformation:DescribeStacks`.
4. **Set up GitHub.** Create the environments `staging` and `prod`.
   - Give `prod` required reviewers (the engineering lead and the HR head's delegate).
   - Set the repository variable `AWS_DEPLOY_ROLE_ARN` to the role's ARN.
5. **Get a certificate.** In ACM, in **ap-south-1**, request a certificate for the stage's name (for
   example `ipro-staging.ideassion.com`) and validate it by DNS.
6. **Sign-in and integrations:**
   - **Entra:** register the iPro app.
     - Redirect URI: `https://<name>/api/auth/callback`.
     - Groups claim on.
     - Microsoft Graph application permissions for guest invitations (and, later, mail and account
       disabling).
     - Create the pre-joiner group.
   - **Zoho Sign:** create an API client, and a webhook with a signing secret pointing at
     `https://<name>/api/esign/webhook`.

## Per stage: settings and secrets

1. **Fill in `infra/stages/<stage>.json`** in a pull request: the domain name, certificate ARN, tenant
   id (a new UUID), Entra tenant and client ids, Zoho client id, Graph client id and pre-joiner group.
   - None of these are secret.
   - Teams, mail and Ask iPro start as `none`. Turn each on later by changing its provider here and
     adding its secret.
   - A deploy refuses to run while any value is still `REPLACE_ME`, and names each one.
2. **Create the repositories and the secret.** Run the Deploy workflow for the stage with
   **prereq_only** ticked.
3. **Fill in the app secret.** Open `ipro/<stage>/app` in Secrets Manager (ap-south-1), replace every
   `REPLACE_ME`, and save:

   | Key | Where it comes from |
   | --- | --- |
   | `ENTRA_CLIENT_SECRET` | the Entra app's client secret |
   | `GRAPH_CLIENT_SECRET` | the Graph app's client secret (can be the same app) |
   | `ZOHO_SIGN_CLIENT_SECRET`, `ZOHO_SIGN_REFRESH_TOKEN` | the Zoho Sign API client |
   | `ZOHO_SIGN_WEBHOOK_SECRET` | the Zoho Sign webhook's signing secret |
   | `TEAMS_BOT_APP_SECRET` | the Teams bot, once registered; until then any value except `REPLACE_ME` |

   - The API refuses to start while any of these is still `REPLACE_ME`. The deploy then rolls back,
     and the API logs name the setting.
   - The database password is generated by AWS and never handled by people.

## Deploying

1. Merge to `main`. CI must be green.
2. Go to **Actions → Deploy → Run workflow**, choose the stage, and run it. Production waits for a
   reviewer.
3. The workflow then:
   - updates the repositories and secret stack;
   - builds and pushes both images, tagged with the commit;
   - deploys the Hyderabad, Mumbai and key-replica stacks with that tag;
   - checks `https://<name>/api/health` through the load balancer.
4. **First deploy only:** point the stage's DNS name at the load balancer. Its name is the
   `LoadBalancerDns` output of `ipro-<stage>`; use a CNAME, or an alias record in Route 53.
5. **Check it:** sign in, check in, apply leave. For staging, then run the go-live checks:
   - the restore test (`docs/runbooks/backup-restore.md`);
   - the pilot (`docs/pilot/pilot-script.md`);
   - the penetration test (`docs/security/pentest-scope.md`).

## Rolling back

- **Failed health checks** roll back by themselves.
- **To go back to an earlier commit** that's already been deployed, run the workflow from that commit.
  Its images are still in the repository; the last 30 are kept.
- **Migrations only move forward.** Write each one so the previous version still works while both run
  during a deploy: add first, remove a release later. A migration that can't be undone that way needs
  a restore (`docs/runbooks/backup-restore.md`).

## Loading the data

The database starts empty apart from the tenant. HR loads people, KYC, balances and history with the
import screens (A6; decisions #94, #95), staging with anonymised data first.
